# 大厅搜索与推荐入口 — 开发设计方案

把首页从「15 张同等主题卡」改成「搜索进入任意概念，推荐位人工指定」。图谱种子保持只读。用户共建主题卡只在本文冻结行为，不进入前两步实现。

与 `docs/ENTRY_AND_HOW_TO_RESEARCH.md`、`docs/FOOD_CARDS_AND_SIDEBAR_LINK.md`、`docs/CONTRIBUTION_MODEL.md`、`docs/DATA_STORE_DECISION.md` 对齐。教育边界不变：文案说明资料里如何一起讨论，不产生诊疗结论。

## 1. 决定

| 步骤 | 交付 | 本步不做 |
|------|------|----------|
| 一步 | 大厅搜索查询全图；选中节点后以该节点为一跳透镜进入探索，并默认隐藏邻域以外的节点 | 从 15 张主题里自动挑一张；大模型生成引导语 |
| 二步 | 推荐位只留人工指定的三枚入口；其余疾病卡收进「按结局浏览」 | 按边数排序；把对照锚点并进同一张图 |
| 三步 | 用户提议主题卡、审核、留言、「大家在看」 | 前两步不实现；不改边、摘录、方向 |

前两步不新增数据库，不改 `data/seed_triples_v0.3_aligned.json`，不改 `DISCLAIMER_TEXT`。

## 2. 为什么不能沿用现在的搜索

探索页 `searchGraph`（`src/lib/search.ts`）有三条和本方案冲突的行为：

1. 调用处把范围限制在**当前已经画出的节点和边**（`src/App.tsx` 把 `rendered` 传进 `searchGraph`）。大厅还没有画布，这个范围是空的。
2. 匹配是子串包含，顺序按种子数组顺序。`糖尿病` 会先碰到别名「糖尿病足溃疡」；`素食` 会碰到「番茄红素食品」里的连续二字。
3. 「隐藏非匹配节点」只看疾病、机制、食物三个过滤锚点（`focusedNodeIds`）。点击聚焦（`clickFocusId`）只影响高亮，不单独决定隐藏。`?node=` 是侧栏选中，省略 `hide` 时默认关闭。因此只设置选中节点，用户仍会看到全图。

大厅搜索需要自己的匹配函数，以及一个新的透镜锚点。

## 3. 信息架构

健康域大厅从上到下：

1. 现有标题区（`LOBBY_KICKER`、`LOBBY_TITLE`、饮食孪生入口、`LOBBY_TAGLINE`）。`LOBBY_INTRO` 改成搜索引导，见第 8 节。
2. **搜索框**。占首位，宽度与标题区对齐。只建议节点，不建议边的 `relation` 句子。
3. **先看这些**。三枚，顺序固定：
   - 植物性饮食：现有主题 `plant-based`，锚点 `plant_based_diet`
   - 动物性食物：透镜，锚点 `animal_foods`（种子节点，不是主题 id）
   - 添加糖：透镜，锚点 `added_sugar`
4. **从食物看**。保留现有 `ultra-processed`、`dietary-fiber`。`plant-based` 从这一排移到推荐，避免同一入口出现两次。
5. **按结局浏览**。`HOME_HEALTH_THEMES` 九张卡放进默认收起的 `details`。文案保持各卡现有 `title` / `blurb`。
6. **素食饮食方式**。`DIET_PATTERN_CARDS` 与「在图谱里了解素食」保持不动，后者仍进入 `plant-based`。
7. **进阶：机制与饮食**。现有 `mechanism-fold` 保持默认收起。

非健康域仍走 `DomainEmptyState`，不渲染搜索结果。

推荐位的「植物性饮食」使用现有 `ThemeCard` 与 `onEnter`。两枚对照使用同一卡片外观，点击走透镜入口，不写入 `diseaseId` / `mechanismId` / `foodId`。

## 4. 一步：搜索与透镜

### 4.1 匹配

新增 `searchNodes(query, nodes)`，大厅与以后的全图搜索共用。不扫描 `links[].relation`。

把标签和每个别名按 `/`、`／`、`、`、空白拆成片段。查询去掉首尾空白后按小写比较。一个节点取它所有片段里的最高档：

| 档 | 条件 | 排序值 |
|----|------|--------|
| 完全一致 | 某个片段与查询相同 | 3 |
| 开头一致 | 某个片段以查询开头，且查询短于该片段 | 2 |
| 不匹配 | 其余情况，包括查询只出现在片段中间 | 0 |

`番茄红素食品` 对查询 `素食` 不得分。`糖尿病足溃疡` 对查询 `糖尿病` 得 2 分。`Ⅱ型糖尿病` 的别名 `糖尿病` 得 3 分，排在前面。

同档内：片段更短的在前；仍相同则按 `label.localeCompare(..., 'zh')`。大厅下拉最多 8 条。空查询不请求、不展示列表。零命中展示第 8 节的空状态，不改推荐主题，不模糊匹配到某张疾病卡。

探索页里的现有搜索保持「只搜当前可见图」，本步不改它的范围。它继续可以搜关联句子。大厅不调用那条路径。

### 4.2 透镜锚点

`focusedNodeIds` 增加可选的 `lensId`。它与疾病、机制、食物一样取一跳邻域（节点自身加上直接相连的节点）。

四个锚点同时存在时仍然取交集。大厅搜索和对照卡进入时只设置 `lensId`，并清空疾病、机制、食物，所以交集不会把结果收成空集。

点现有主题卡时清空 `lensId`，行为与今天一致。

`hide` 的默认值：探索页带 `lens` 时与带 `theme` / `disease` / `mechanism` / `food` 相同，省略则视为打开。`hide=0` 仍可显式关闭。

URL 新参数 `lens=<nodeId>`。`node=` 继续只表示侧栏选中，两者可同时存在。序列化时：

- `lens` 有值则不写出 `theme`、`disease`、`mechanism`、`food`。
- 节点 id 用现有 `cleanId`。种子里不存在的 id 在解析后丢弃，不当成锚点。
- 同时出现 `lens` 与 `theme` 时，以 `lens` 为锚点，忽略 `theme`。

进入探索后：`clickFocusId` 与侧栏选中设为该节点，视图保持用户当前的 `view`（缺省仍是通路）。统计文案沿用「当前可见 …」。透镜没有主题芯片的按下态。探索侧栏主题列表里不因此高亮任何一张卡。

### 4.3 层次视图的边预算

通路视图已有 `FLOW_BAND_BUDGET = 36`（`selectFlowBands`）：超出预算的边留在数据里，不画成带子。

层次视图（`view=2d`）今天会画出邻域内部的全部边。植物性饮食的一跳是 36 个节点、119 条边；搜索若打开「肠道菌群多样性」（59 条直接边），层次会比现有主题更密。

本步只在「隐藏非匹配节点」打开、并且已有主题或透镜锚点时，让层次视图使用同一预算，且只限制**画出的边**，不删节点。没有锚点的层次视图仍画出全部边：

- 可见节点仍是透镜或主题的一跳（在 `hide` 打开时）。
- 候选边是两端都在可见节点里的边。
- 排序复用 `selectFlowBands` 的优先级：锚点直接相连的边优先，其次强度与证据条数。同列边在通路里不画；层次里同列边可以画，但同样计入 36 条预算。
- 超出预算的边不进入层次的绘制数据。通路视图逻辑不变。
- 预算生效且有边被省略时，层次 HUD 使用第 8 节的句子。未省略时不显示这句。

被省略的边仍在种子和探索页搜索里。探索页搜索的范围是「当前可见节点」，不是「当前画出的边」。用户搜到邻域内的节点后可以点选，侧栏仍打开对应资料。

## 5. 二步：推荐位

推荐名单写在新常量 `LOBBY_RECOMMENDED`（建议放在 `src/lib/lobbyEntry.ts`），不按度数生成，测试锁住顺序与锚点 id：

| 顺序 | 标签 | 种类 | 锚点 |
|------|------|------|------|
| 1 | 植物性饮食 | 主题 `plant-based` | `plant_based_diet` |
| 2 | 动物性食物 | 透镜 | `animal_foods` |
| 3 | 添加糖 | 透镜 | `added_sugar` |

主卡视觉重量高于两枚对照（对照用次级按钮或较小卡片）。三枚都在首屏搜索框下方，不折叠。

「按结局浏览」的 `summary` 文案见第 8 节。展开后仍是现有九张 `ThemeCard`，id 与过滤不变。

对照锚点若在以后的种子里被删除，该入口不渲染，测试在当前种子上断言两个 id 存在且类型分别为 `food_category`。

## 6. 三步：用户主题卡（冻结，不在前两步实现）

触发条件：一步和二步已合并，并且需要网站内提交与审核。按 `docs/DATA_STORE_DECISION.md`，这时再引入独立的动态存储。种子 JSON 与 `themes.ts` 里的系统主题仍只经 PR 变更。

一张用户主题卡只包含：

- 问句标题（上限与现有 `blurb` 一样收紧，标题建议不超过 40 字）
- 简介，不超过 40 字
- `anchorNodeId`：必须是当前种子中的节点 id
- 状态：`pending` / `published` / `rejected`

同一 `anchorNodeId` 已有 `published` 卡时，提交接口拒绝新建，并返回那张卡的 id，界面引导去留言。

公开规则：

- 卡片先审后发。提交时用第 8 节的禁词表拒绝。
- 留言可先发，管理端可隐藏。留言的外键是卡片 id。图谱抽屉不读取留言。
- 「大家在看」只含 `published`。排序键是近 14 天的独立打开次数，按天衰减（更早的一天权重更低）。不用留言数。没有计数时不渲染这一排。
- 大厅搜索仍先按第 4 节排节点。`published` 卡的标题只有在节点结果之外、且标题片段命中时才作为附加行出现，不多于 3 条。附加行进入的是该卡的锚点透镜，不是一张新的图。

本步需要登录后才能提交。前两步不添加账号。

## 8. 文案

新字符串放在 `src/lib/exploreShell.ts`。`palette.test.ts` 里 `LOBBY_INTRO` 的全文断言要同步改。禁止出现：治疗、治愈、处方、请服用、停药、替代医生、GRADE、降低、预防、逆转、疗效、防治、患者、建议你吃。`LOBBY_INTRO` 继续不要包含「不是医疗建议」（免责声明只留在页脚）。

| 键 | 文案 |
|----|------|
| `LOBBY_INTRO` | 输入想了解的食物、机制或健康主题，或从下面几项看资料里的讨论。 |
| `LOBBY_SEARCH_PLACEHOLDER` | 输入想了解的概念 |
| `LOBBY_SEARCH_EMPTY` | 资料里还没有这个概念 |
| `LOBBY_RECOMMENDED_HEADING` | 先看这些 |
| `LOBBY_CONTRAST_NOTE` | 对照着看资料里另一类食物如何被讨论 |
| `LOBBY_OUTCOMES_SUMMARY` | 按结局浏览 |
| `HIERARCHY_BUDGET_NOTE` | 这一视图画出 36 条关联，其余仍留在资料和搜索里。 |

`HIERARCHY_BUDGET_NOTE` 里的 36 与 `FLOW_BAND_BUDGET` 用同一常量格式化，避免两处数字漂移。

区块标题用「先看这些」，不用「推荐」。全站文案守卫把「推荐」当作处方式用语，标题若用这个词，就得把守卫从整个 `src` 里拿掉。

## 9. 测试

`npm test` 需覆盖：

- `糖尿病`：`type2_diabetes` 排在别名含「糖尿病足溃疡」的节点之前。
- `素食`：`plant_based_diet` 命中；`tomato` 不命中。
- `痛风`：命中 `gout_uric_acid`（标签片段「痛风」完全一致）。
- `脂肪肝`：命中 `fatty_liver`。
- 空查询与无命中：结果为空，调用方不改推荐列表。
- `?lens=animal_foods` 解析为透镜，`hide` 省略时为打开；未知 id 被丢弃。
- 序列化透镜时不带 `theme`、`disease`、`mechanism`、`food`。
- `?lens=plant_based_diet&theme=fatty_liver` 的有效锚点是透镜。
- `focusedNodeIds` 在只传 `lensId` 时等于该节点的一跳。
- 层次预算：邻域边数大于 36 时画出 36 条，且锚点的直接边优先于邻域内部的其他边。
- 推荐常量的三个锚点顺序，以及 `animal_foods`、`added_sugar` 存在于当前种子。
- 新文案不含第 8 节的禁词。

前两步跑 `npm test`。不改种子，不必为这两步单独跑 `validate:data`，除非改动波及 `data/`。

## 10. 验收

1. 打开大厅。搜索框在推荐主题之上。输入 `痛风` 能进入「高尿酸血症 / 痛风」的一跳，且邻域以外的节点被隐藏。
2. 输入 `素食`，第一条是植物性膳食，列表里没有番茄。
3. 输入一个种子里不存在的词，看到「资料里还没有这个概念」，推荐区仍在。
4. 推荐第一张是植物性饮食。动物性食物、添加糖各打开自己的一跳，不把三张图叠在一起。
5. 「按结局浏览」默认收起；展开后九张疾病卡的 id 与过滤与现在相同。
6. 素食饮食方式板块仍可进入 `plant-based`。
7. 打开植物性饮食后切到层次：画出的边不超过 36，HUD 说明其余关联仍在资料和搜索里。通路视图的带子预算行为与现在一致。
8. 复制链接再打开，透镜与 `hide` 状态保持。`node=` 仍只恢复侧栏选中。

## 11. 非目标

- 不按节点边数自动生成或排序推荐。
- 不把 15 张主题卡从探索侧栏删除。
- 不在抽屉中展示留言，不把用户文本写入 `direction` 或摘录。
- 不在前两步登录、审核或存储用户卡片。
- 不修改免责声明原文。
